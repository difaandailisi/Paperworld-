# 瞬时界面：把「用完即销毁的 APP」说清楚

> 源文档：`difaandailisi/Paperworld-` 的 README（2023-03 提交，构想始于 2020）
> 本文任务：把你 2020 年那句"说不清是菜单还是 APP、生成后立即销毁、但数据保持不变"翻译成
> 可检验的技术命题，并用今天的 AI 理论与 MCP 重新表述。
>
> 结论先给：**你不是说错了一个词，你是撞上了一类还没有名字的东西。**

---

## 一、先把你那句话拆成三个可检验的命题

原话：

> "AI 可以直接生成一份我不知道叫他菜单还是叫他 APP，就是使用立即生成，生成之后再销毁。但是数据保持不变。"

这句话里其实压着三件事，它们各自独立，可以分别成立或证伪：

| # | 命题 | 形式化表述 | 今天成立吗 |
|---|---|---|---|
| P1 | **界面可以不是资产** | 界面 = f(状态, 意图)，随用随算，不必预先存在 | ✅ 成立 |
| P2 | **生命周期可以短于产品周期** | 生成物的寿命 = 本次使用时长，而非软件版本周期 | ⚠️ 部分成立 |
| P3 | **状态与界面可以彻底解耦** | 状态持久化，界面可丢弃，丢弃界面不损失信息 | ✅ 成立 |

你纠结"叫菜单还是叫 APP"，本质是 **P1 和 P2 同时成立时，旧词汇失效了**：

- 叫**菜单**，隐含"功能已经存在，我只是把它列出来"——但功能是现生成出来的，不存在索引关系。
- 叫**APP**，隐含"预装、常驻、有版本号、可卸载"——但它可能只活 90 秒，没有版本，谈不上卸载。

两个词都默认了"软件是一个**持久物件**"。你描述的恰恰是**软件作为一次事件**。

---

## 二、你今天这句话有一半已经有名字了

### 2.1 界面不是资产，是投影 —— Generative UI

现代前端已经在往这个方向走：**Generative UI**（生成式界面）主张界面不是预先写死的组件树，
而是由模型根据当前数据与用户意图，在运行时组装出来的结构。

它的理论前提是一个很朴素的等式：

```
UI = render(State, Intent)
```

传统应用把 `render` 编译成固定的组件树，一次写好、长期复用；
你的想法是把 `render` 也变成运行时计算的一部分——**每次调用都重新求解，解完即弃**。

这一步在数学上没有任何障碍。障碍全在工程上（见第五节）。

### 2.2 你真正提出的，是"软件作为一次性消耗品"

这是你原话里最有价值、也最容易被忽略的部分：**"生成之后再销毁"**。

软件工程六十年来的默认假设是：软件是**耐用品**。我们为它做版本管理、做向后兼容、
做灰度发布、做十年维护。你这个想法直接把这个假设掀了：

| | 耐用品范式 | 一次性范式（你的构想） |
|---|---|---|
| 生命周期 | 年 / 十年 | 秒 / 分钟 |
| 版本 | 有 | 无（每次都是新生成） |
| 兼容性 | 必须向后兼容 | 不需要，用完即弃 |
| 复用方式 | 代码复用 | **意图复用 + 状态复用** |
| 失败代价 | 高（影响所有用户） | 低（只影响这一次） |
| 沉淀的是什么 | 代码 | **数据 + 语义** |

注意最后一行——**沉淀的对象换了**。这正是你说的"数据保持不变"为什么关键：
在一次性范式里，唯一需要长期稳定的东西只剩状态与语义，界面退化成了一次性的**渲染结果**。

这个思路在今天的语境里可以对应到几个已有的提法：**ephemeral software**、
**just-in-time interface**、**software as a disposable artifact**。
它们都还不算成熟学科，但指向同一件事。

### 2.3 MCP 恰好是这件事的骨架

这是最关键的一节。你问"结合 MCP 改造一下"——实际上 MCP 的协议设计**天然就在为这个范式铺路**。

MCP（Model Context Protocol）把模型能接触的世界切成三类原语：

| MCP 原语 | 是什么 | 在你的构想里对应什么 | 生命周期 |
|---|---|---|---|
| **Tools** | 可调用的动作（有副作用） | 能力 | 长期稳定 |
| **Resources** | 可读取的数据/上下文 | 状态、你的"原子化标签" | 长期稳定 |
| **Prompts** | 预置的交互模板 | 常用意图的快捷方式 | 长期稳定 |

请注意这三样**没有一样是界面**。

这意味着：MCP 在协议层面已经把「**能力与状态**」和「**界面**」拆开了。服务端只负责
"你能做什么、你能读什么"，至于这一次用什么形式呈现给用户——菜单、卡片、表单、一段对话、
还是一条语音回复——**协议不管，由客户端当场决定**。

换句话说：

> **MCP 服务器是长期的，界面是当场的。**
> 你要的"生成即用、用完即销毁、数据不变"，就是 MCP 客户端的一层渲染策略。

这解释了为什么你的直觉在 2020 年是超前的：那时候没有这层抽象，你只能在"APP"和"菜单"
之间二选一；现在有了，两个都不用选。

### 2.4 你的"原子化标签" = 语义层

原文 2.2 / 2.3 / 2.4 反复讲一件事：把环境、输入、用户操作都转成**原子化标签**，
按主题归类入库，然后供检索与推荐使用。

这在今天的术语里叫 **语义层（semantic layer）** 或 **本体（ontology）**，在工程上通常落成：

- 实体 + 关系 → 知识图谱（你原文 4.3 已经写到）
- 特征 → 向量嵌入（embedding），用于相似检索
- 事件 → 追加日志（event log）

你原文说的"超模态拓展可视化大一统场景数据库"，如果剥掉修辞，接近今天说的
**多模态统一表示 + 统一查询层**。方向对，但实现代价被原文严重低估了。

### 2.5 你的"低代码 → AI 生成产品" = 程序合成

原文 1.24 有一句非常关键的话：

> "在早期，这只是一种低代码技术产生更多的是模板，在 AI 的加入后很快变成了可迭代，高稳定性的产品。"

这是**程序合成（program synthesis）** 的直觉版本：用户给规格（模板/草图/自然语言），
系统产出可运行的东西。而"可迭代、高稳定性"这两个词恰好点出了今天最大的难题——
**一次生成容易，稳定地反复生成同质量的东西极难**。

## 三、命名问题：它既不叫菜单，也不叫 APP

既然 P1+P2 成立，我们需要一个新词。命名不是文字游戏——**名字决定了你怎么设计它**。

叫"菜单"，你会去优化索引与检索；
叫"APP"，你会去优化打包与分发；
这两个方向都会把你带偏。真正该优化的是**生成质量与销毁的干净程度**。

我建议两个候选，任选：

**候选一：瞬时界面（Ephemeral Surface）**
强调"存在过但不再存在"。技术含义：一个生命周期绑定到单次会话、不进入持久存储的渲染产物。

**候选二：一页纸（A Page）**
这个更贴你"纸世界"的原始意象。逻辑是：

- 你每次需要什么，就从纸堆里**抽一张纸**
- 这张纸可以是表格、可以是图表、可以是一个小工具、可以是一段对话
- 用完**揉掉烧掉**
- 但纸上写的字，已经进了**账本**（持久数据）
- 下次要用，重新抽一张——形状可能完全不同，但内容连着

"一页纸"这个隐喻顺带解决了你原文里另一个纠结：**"每一次打开都是空白"**。
空白不是没有内容，空白是**尚未决定这一页要长成什么样**。

## 四、参照架构

把上面几节拼起来，一个可以真正开始动手的结构长这样（自下而上）：

```
┌─────────────────────────────────────────────┐
│ L5  销毁层   会话结束 → 界面 GC，保留操作 trace  │  寿命：秒~分钟
├─────────────────────────────────────────────┤
│ L4  合成层   意图 → 界面规格 → 渲染             │  每次重新求解
├─────────────────────────────────────────────┤
│ L3  意图层   自然语言/手势 → 结构化意图 → 计划   │  每次重新解析
├─────────────────────────────────────────────┤
│ L2  能力层   MCP: tools / prompts              │  长期稳定
├─────────────────────────────────────────────┤
│ L1  语义层   实体图谱 + 向量索引 + 原子标签      │  长期演进
├─────────────────────────────────────────────┤
│ L0  状态层   追加日志（唯一真相）+ 投影视图      │  永久
└─────────────────────────────────────────────┘
```

### 一次完整生命周期的七步

拿"我想看看这支笔这周的电量怎么样"举例：

1. **意图**：用户说一句话。L3 解析成 `{实体: 手写笔, 指标: 电量, 时间窗: 本周, 动作: 查看趋势}`
2. **取数**：L2 调 MCP 的 `query_battery_records` 工具，L1 用语义层补全"这支笔"指哪支
3. **决策形状**：判断这次该给什么——数据量小给一张卡片，有明显趋势给折线图，异常给告警列表
4. **合成**：L4 生成界面规格（不是代码，是规格），客户端渲染出来
5. **使用**：用户看了一眼，划掉两个异常点
6. **回写**：这两个标注作为事件写进 L0 日志——**这是唯一被持久化的东西**
7. **销毁**：界面消失。下次问同样的问题，可能给你一张完全不同的图，但数据是连着的

**第 6 步是整个架构的重心。** 如果销毁时什么都没留下，这个系统就退化成"每次重新问一遍"；
只有把"用户在这次界面里做了什么"沉淀成事件，销毁才是无害的。

## 五、现在能做什么，现在做不到什么

这一节必须说得直白，否则就会变成又一份科幻稿。

### 已经可以落地的

| 能力 | 现状 |
|---|---|
| 按意图动态选界面形态（卡片/表格/图表/对话） | ✅ 成熟，本质是"模板选择 + 参数填充" |
| 工具调用与能力编排 | ✅ MCP 已标准化 |
| 状态与呈现解耦 | ✅ 这是好架构本来就该做的 |
| 生成简单的一次性小工具（计算器、临时筛选器） | ⚠️ 可行但稳定性一般，适合低风险场景 |
| 从自然语言生成结构化查询 | ✅ 成熟 |

### 现在做不到、或代价过高的

| 能力 | 卡在哪 |
|---|---|
| **完全无预设的界面生成** | 每次从零生成 UI 的**延迟与成本**不可接受；实际系统都会退化成"生成配置 + 复用模板" |
| **保证生成质量稳定** | 同一意图生成两次结果不一致，用户会失去肌肉记忆。**这是这个范式最大的敌人** |
| **销毁的彻底性** | 界面容易销毁，"副作用"不容易——生成的东西如果改了数据，回滚很难 |
| **可发现性** | 用户不知道能要什么。传统 APP 靠图标列表解决，你的范式没有图标，这是真问题 |
| **可测试性** | 没有固定界面就没有回归测试，也没法做 A/B。工程上会非常痛 |
| **无障碍** | 键盘快捷键、读屏器、焦点顺序，动态生成的界面很难保证 |

### 关于你原文里那些更远的部分

你的 README 里还有电子纸硬件、盖亚系统、区块链存储激励、纳米芯片等设想。
这些不属于本文范围，但需要诚实标注：**它们是 2030+ 的硬件与制度问题，与"瞬时界面"
这个软件构想可以完全解耦**。也就是说——**你不必等电子纸成熟，今天就能验证 P1/P2/P3。**

## 六、五个真问题（决定这个范式生死的地方）

### 问题 1：生成的不确定性 vs 用户的肌肉记忆

人依赖"同一个按钮在同一个位置"。你的范式每次生成都可能换位置、换形态。
**解法方向**：区分"可变的呈现"与"不可变的手势契约"——形态可以变，
但"划掉=删除""长按=更多"这类元操作必须稳定。就像纸质笔记本：每页内容不同，但翻页方式永远一样。

### 问题 2：延迟

生成需要时间，传统 APP 点击即响应。**解法方向**：预取 + 投机生成（猜你接下来要什么，提前算好），
以及"先用粗糙形态顶上，再渐进细化"。这本质上和当年云端独占翻车（你原文引用了 NEW BING 的案例）
是同一个问题的现代版本。

### 问题 3：安全边界

动态生成的界面如果携带动作，就必须有**能力授权**。这正是 MCP 的 tools 原语要解决的问题：
**界面可以是生成的，但可调用的能力必须是声明过、被授权过的**。
生成器只能在白名单能力里组合，不能凭空创造一个能删数据的按钮。

### 问题 4：可发现性

"我不知道该叫它什么"——这个困惑会原样传递给用户：
**用户也不知道该跟它要什么。** 传统 APP 用图标网格解决发现性问题，瞬时界面没有图标。
**可能的解法**：保留一个极小的"常驻锚点"（少数高频意图的快捷入口），
其余全部按需生成。这等于承认：**这个范式不是要消灭 APP，而是把 APP 从"全部"压缩到"头部 5%"**。

### 问题 5：什么该被沉淀

如果什么都沉淀，语义层会迅速腐化；如果什么都不沉淀，系统永远不认识你。
**解法方向**：只沉淀两类东西——**用户做过的判断**（标注、选择、否决）和**被反复请求的意图**。
前者是偏好，后者是需求。中间过程一概丢弃。

## 七、最小可行实验

不要一上来做纸世界。用两周验证 P3（状态与界面解耦）就够了：

**实验设计**

1. 选一个真实场景（比如你自己的手写笔电量数据）
2. 底层只做一件事：把数据写成**追加日志**，并提供 3~5 个 MCP 工具（查询、筛选、标注）
3. 上层**不做固定界面**，每次用自然语言问，让模型决定这次输出成什么形态
4. 关键测量：**同一问题问三次，界面形态是否会变？用户会不会觉得困扰？**
5. 关键验证：**销毁界面后，第二次提问能否接上第一次的上下文？**

第 4 步测的是"不确定性代价"，第 5 步测的是"状态解耦是否真的成立"。
这两个数据出来，你就知道这个方向值不值得继续。

## 九、一句话

你 2020 年说的那句话，准确版本是：

> **软件正在从"耐用品"变成"消耗品"；界面从"资产"退化为"投影"；唯一长期存在的，是状态与语义。**

"MCP" 之所以重要，不是因为它是个新协议，而是因为它**在协议层面承认了界面不该被固化**——
它只标准化能力与数据，把"这一次长什么样"留给当场决定。

这恰好是你六年前想说、但当时没有词可以说的事。
