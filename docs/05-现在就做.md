# 现在就做：从零到第一个可验证实验

> 这份文档不讲理念。它假设你已经读完 [`02-瞬间重构-纸世界.md`](02-瞬间重构-纸世界.md)，
> 现在想知道：**明天早上打开电脑，第一步敲什么。**
>
> 全篇围绕一个目标——**不是做产品，是拿到一个数。**

---

## 0. 你要证明的只有一件事

整套构想里，只有一条是"不做就永远不知道"的：

> **生成、使用、销毁，重复 100 次之后，系统状态和"从来没生成过"完全一致。**

这在论文里叫**汇流性**。它不是体验问题，不是性能问题，是**正确性问题**——
如果这一条不成立，你的"用完即弃"就是在泄漏，跑一天系统就烂了，后面所有构想全部作废。

**所以第一个实验的全部目的，就是测出这个数。**

两周。一个数字。过了，你有资格继续；不过，你省下了六个月。

## 1. 动手前必须做的三个决定

这三个决定会影响后面每一行代码，先钉死。

| # | 决定 | 推荐答案 | 理由 | 备选 |
|---|---|---|---|---|
| **D1** | 用什么数据 | **你手写笔 App 里的电量记录** | 你已经有了真实数据（Room 库里就有），不用造；而且它有"判断"可做（哪段算异常放电） | 记账、运动记录、阅读笔记 |
| **D2** | 跑在哪 | **本地网页**（Node + 浏览器） | Widget 生态全在 Web：MCP Apps、OpenAI Apps SDK 的宿主渲染模型都是 iframe + postMessage。Android 原生要自己造轮子，两周做不完 | Android + Compose（慢 3 倍） |
| **D3** | 生成到什么粒度 | **只生成配置，不生成代码** | 配置是 JSON，可校验、可回滚、延迟低；生成代码会带来无法预估的失败面 | 代码生成（B 级，先别碰） |

**D3 最重要。** 很多人一上来就想"让 AI 写界面代码"，那是给自己挖坑。
你要的是：AI 决定**这次该用哪种形态、装哪些数据、给哪些操作**，然后由你写好的四套模板渲染出来。

## 2. 技术栈（可以直接抄）

| 层 | 用什么 | 为什么是它 |
|---|---|---|
| **状态层** | SQLite + 只追加表（`better-sqlite3`） | 单文件、零部署、可 `SELECT` 重放 |

| **能力层** | `@modelcontextprotocol/sdk`（TypeScript） | MCP 是当前事实标准，能被任意客户端调用 |
| **合成层** | 任意 LLM + **JSON Schema 约束输出** | 关键是"约束"，不是"哪个模型" |

| **验收** | 一个 Node 脚本 + 一次哈希比对 | 这就是你要的结论 |

### Step 1 · 状态层：只追加，永不修改（1 天）

```sql
CREATE TABLE events (
  id      INTEGER PRIMARY KEY AUTOINCREMENT,
  ts      INTEGER NOT NULL,        -- 毫秒时间戳
  kind    TEXT    NOT NULL,        -- battery_reading | user_judgment | session_start | session_end
  entity  TEXT    NOT NULL,        -- 设备 mac
  payload TEXT    NOT NULL         -- JSON
);
CREATE INDEX idx_entity_ts ON events(entity, ts);
```

**三条纪律**：

1. **永不 `UPDATE`，永不 `DELETE`**。写错了就再写一条"更正"事件。
2. **界面的每一次操作都要落成事件**，尤其是"用户看了、划掉了、标注了"。
3. 当前视图是**算出来的**，不是存下来的。

**验收**：从空库开始重放全部事件，能得到和当前一致的视图。这一步做不到，后面全废。

### Step 2 · 可逆效应：整个实验的心脏（2 天）

这是唯一必须"手写"的部分。六十行，不依赖任何库：

```ts
// effect.ts —— 可逆效应的最小实现
type Inverse = () => void | Promise<void>;

export class Context {
  private inverses: Inverse[] = [];

  /** 施加一个副作用，同时登记它的逆 */
  effect<T>(apply: () => T, revert: Inverse): T {
    const value = apply();
    this.inverses.unshift(revert);   // 前置累积 → 天然 LIFO 回收
    return value;
  }

  /** 卸载：倒序执行全部逆操作 */
  async dispose(): Promise<void> {
    for (const inv of this.inverses) {
      try { await inv(); } catch (e) { console.error("[dispose]", e); }
    }
    this.inverses = [];
  }
}
```

用起来是这样——**每一个"登记"都必须配一个"撤销"**：

```ts
const ctx = new Context();

ctx.effect(
  () => window.addEventListener("resize", onResize),
  () => window.removeEventListener("resize", onResize),
);

ctx.effect(
  () => { const id = setInterval(poll, 5000); return id; },
  () => clearInterval(pollId),
);

ctx.effect(
  () => db.prepare("INSERT INTO events ...").run(...),   // 写数据
  () => {/* 数据不回滚，只回滚"副作用"——见下面的坑 */}
);
```

**⚠️ 这里有个坑必须想清楚**：数据写入**不该**被撤销（那违反"数据不变"）。
可逆效应撤销的是**资源与订阅**：监听器、定时器、连接、DOM 节点、临时文件。
**"写事件"是留痕，不是副作用。**

**验收**：连续 `mount → dispose` 100 次，进程内存不增长、监听器数量回到 0。

```ts
// 怎么验：Node 里测
for (let i = 0; i < 100; i++) { const c = mount(); await c.dispose(); }
assert.equal(process.listenerCount("SIGINT"), baseline);
```

### Step 3 · 能力层：三个 MCP 工具（2 天）

只做三个，不要多：

| 工具 | 参数 | 返回 |
|---|---|---|
| `query_battery` | `{device, from, to, granularity}` | 电量序列 |
| `find_anomalies` | `{device, from, to}` | 异常区间列表 |
| `annotate` | `{eventId, label, note}` | 写入一条 `user_judgment` 事件 |

```ts
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { z } from "zod";

const server = new McpServer({ name: "pen-battery", version: "0.1.0" });

server.tool(
  "query_battery",
  { device: z.string(), from: z.number(), to: z.number() },
  async ({ device, from, to }) => ({
    content: [{ type: "text", text: JSON.stringify(queryEvents(device, from, to)) }],
  }),
);
```

**验收**：用任意 MCP 客户端（Claude Desktop、dsh、或自己写的 CLI）能成功调用并拿到数据。

**为什么这层要独立**：因为它是**长期的**。界面每次销毁，工具不动。这就是"能力持久、界面临时"。

### Step 4 · 合成层：意图 → 界面配置（3 天）

定义四种形态的配置 schema：

```json
{
  "form": "line | table | card | list",
  "title": "本周电量趋势",
  "dataRef": "query_battery#3",
  "highlight": [{"from": 1730000000, "to": 1730200000, "reason": "异常放电"}],
  "actions": ["annotate", "expand"]
}
```

**关键做法：用 JSON Schema 约束输出，而不是靠提示词描述**。

```ts
const schema = z.object({
  form: z.enum(["line", "table", "card", "list"]),
  title: z.string().max(40),
  dataRef: z.string(),
  highlight: z.array(z.object({ from: z.number(), to: z.number(), reason: z.string() })).optional(),
  actions: z.array(z.enum(["annotate", "expand"])),
});
```

模型输出不合法就重试，最多三次，仍失败则**降级到固定形态**。

**验收**：
- 同一意图跑 10 次，**配置合法率 100%**
- 记录"形态分布"——如果 10 次里有 6 次给同一种形态，说明你的场景其实不需要动态形态（这本身是个重要发现）

### Step 5 · 渲染层：四套模板（2 天）

四个函数，每个吃一份配置吐 DOM：

```ts
const renderers = { line: renderLine, table: renderTable, card: renderCard, list: renderList };

async function mount(config) {
  const ctx = new Context();
  const root = document.createElement("div");

  ctx.effect(
    () => document.body.appendChild(root),
    () => root.remove(),
  );
  ctx.effect(
    () => renderers[config.form](root, config, ctx),   // 模板自己也可能登记副作用
    () => {/* 由各模板在 ctx.effect 里登记 */},
  );

  return ctx;
}
```

**验收**：四种配置都能正确渲染，`dispose()` 后 DOM 节点数回到初始值。

### Step 6 · 汇流性测试（1 天，最重要的一天）

```ts
// confluence.test.ts
const before = hashState(db);           // 全表哈希：SELECT * ORDER BY id，含 rowid

for (let i = 0; i < 100; i++) {
  const cfg = await generate(intent);
  const ctx = await mount(cfg);
  await simulateUserAction(ctx);        // 可选：模拟一次标注
  await ctx.dispose();
}

const after = hashState(db);
assert.equal(before, after, "汇流性失败：销毁留下了残留");
```

**注意**：如果你在 Step 5 里让用户做了标注，`after` 必然 ≠ `before`——
那是**留痕**，不是残留。所以正确做法是**只哈希"资源类状态"**：

```ts
hashState = () => sha256(JSON.stringify({
  domNodes: document.body.childElementCount,
  listeners: countListeners(),
  timers: countActiveTimers(),
  handles: process._getActiveHandles().length,
}));
```

**这就是全部实验的核心产出**：一张 100 次循环前后对比的图。

## 5. 你必须自己找到的东西

这一节是全文唯一不能替你回答的。**下面五个问题答不出来，代码写得再对也没用。**

### ① 在你的场景里，"一个判断"到底是什么？

这决定 `events` 表存什么。手写笔场景里，判断可能是：

- "这段时间掉电异常" → 标注
- "这支笔的续航比上周差" → 结论
- "这条记录是误差，忽略" → 否决

**判断 = 用户看过之后做的、值得下次复用的动作。** 不是浏览，不是滚动。

### ② 一次界面销毁时，cleanup 清单有哪些？

对着你的代码一条条数。典型的：

监听器 / 定时器 / `requestAnimationFrame` / WebSocket / `IntersectionObserver` /
ResizeObserver / DOM 节点 / 临时文件 / Blob URL / Web Worker / 未完成的 fetch

**列成清单贴墙上**，每加一个副作用就对照检查。VSCode 前 100 个扩展里 87 个栽在这上面。

### ③ 一致性 vs 新鲜度，怎么取？

界面显示的数据可以是多旧的？3 秒？1 分钟？还是必须实时？
**这个答案决定了你要不要加订阅/推送**，也决定了 cleanup 里要不要处理连接。

### ④ 信任边界画在哪？

生成的界面能触发什么级别的动作？

| 级别 | 例子 | 建议 |
|---|---|---|
| 只读 | 看图表 | 随便生成 |
| 写本地 | 打标注 | 需要确认 |
| 对外 | 发消息、下单、删数据 | **不要在这个阶段做** |

DSH 把"生成即可执行"的信任等级标在 shell 权限上，还**默认关闭**。你也该这样。

### ⑤ 你能接受多大的"形态不稳定"？

问自己：如果同一个问题，今天给你折线图、明天给你表格，你会烦吗？

**这个答案决定了你要不要加"形态偏好记忆"**——而一旦加了，你就在往"APP"的方向回退。
这是个真实的产品取舍，没有标准答案。

## 7. 五个已知的坑

| 坑 | 为什么致命 | 怎么避 |
|---|---|---|
| 从零生成 UI 代码 | 失败面无法预估，延迟高 | **只生成配置** |
| 忘写 cleanup | 内存泄漏、事件重复触发 | 用 `ctx.effect(apply, revert)` 强制配对；`revert` 必填 |
| 用提示词写约束 | 模型会"理解偏" | 写成 JSON Schema 枚举 |
| 拿成功率衡量 | 很可能测出零，然后误判方向 | 测步数、测停留时间、测误解率 |
| 把"生成"当"智能" | 生成只是编排，不是推理 | 意图解析可以简单规则，值得用模型的是**形态决策** |
