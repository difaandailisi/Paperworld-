# 第一部分　纸世界到底是什么

## 1.1 一句话

> 纸世界不是"一个超级 APP"，而是**把软件的形态从"预先装好的物件"改成"按需生成的临时物"**，
> 只让数据与语义长期存在。

这句话是全篇的锚。下面所有内容都是它的展开。

## 1.2 原始构想的七个部件

把你 2023 年那份 README 剥掉科幻叙事，实际提出的是七件事：

| # | 部件 | 原文主张（摘要） | 本质是什么 | 与核心命题的关系 |
|---|---|---|---|---|
| 1 | **载体** | 电子纸、可折叠、无穷无尽头的一张纸 | 硬件形态 | **可解耦**，与核心命题无关 |
| 2 | **界面** | 每次打开都是空白；功能融合相交，不集成 | 界面不定型 | ★ **核心** |
| 3 | **输入** | 语音、笔、触摸、鼠键、目视 | 多模态入口 | 支撑项 |
| 4 | **转换** | 手写→字体、绘画→表格/网站/知识图谱（"超扩展 aiOCRcode"） | 感知→结构 | ★ 核心的输入端 |
| 5 | **语义** | 环境与输入全部转成"原子化标签"再入库 | 语义层 | ★ **核心** |
| 6 | **生成** | 用户自定义模板 → AI 翻译成"可迭代、高稳定性的产品" | 程序合成 | ★ **核心** |
| 7 | **存储** | 云端 / 分布式 / 盖亚系统 / 区块链激励 | 基础设施 | 可解耦，且政治经济属性强 |

**关键观察**：真正构成"纸世界"这个独特想法的，是 **2、4、5、6 四项**。
1（电子纸）、7（盖亚系统）是包裹在外面的未来设定——**它们可以完全剥离，而不影响核心成立。**

这解释了一件事：为什么这个构想放了六年没法动手。因为它被硬件叙事绑架了。
**你不必等电子纸，就能验证第 2、5、6 项。**

## 1.3 你真正提出的那一条

原话：

> "AI 可以直接生成一份我不知道叫他菜单还是叫他 APP，就是使用立即生成，生成之后再销毁。但是数据保持不变。"

拆成三个可独立检验的命题：

| 命题 | 形式化 | 2026 年状态 |
|---|---|---|
| **P1 界面不是资产** | 界面 = f(状态, 意图)，随用随算 | ✅ 已被工业界部分实现 |
| **P2 生命周期短于产品周期** | 生成物寿命 = 本次使用时长 | ⚠️ 组件级已实现，界面级没有 |
| **P3 状态与界面彻底解耦** | 丢弃界面不损失任何信息 | ✅ 有形式化保证（见 2.2） |

"叫菜单还是叫 APP"的困惑，根源是 **P1+P2 同时成立时旧词汇失效**：

- 叫**菜单** → 隐含"功能已存在，我只是列出来"（但功能是现生成的）
- 叫**APP** → 隐含"预装、常驻、有版本、可卸载"（但它可能只活 90 秒）

两个词都默认**软件是持久物件**。你描述的是**软件作为一次事件**。

## 1.4 剔除幻想的滤网

一条简单判据：**"这件事的瓶颈是算力/材料，还是范式？"**

| 瓶颈类型 | 举例 | 处置 |
|---|---|---|
| 材料 / 制造 | 电子纸、石墨烯芯片、纳米薄膜 | 不是你的战场，**划到 D 区等待** |
| 制度 / 经济 | 盖亚系统、区块链存储激励、"私人存储违法" | 社会议题，与技术构想**解耦** |
| **范式 / 语义** | 界面临时化、状态解耦、能力组合 | ★ **这是你能做的全部** |

判断标准写死在这里，后面第三节直接套用。

## 1.5 命名

| 候选 | 含义 | 适用场合 |
|---|---|---|
| **瞬时界面**（Ephemeral Surface） | 生命周期绑定单次会话、不进持久存储的渲染产物 | 写技术文档时用这个，精确 |
| **一页纸**（A Page） | 抽一张、用完揉掉、字已进账本 | 对用户表达时用这个，直观 |

"一页纸"顺带解决了你原文里"每次打开都是空白"的困惑：
**空白不是没有内容，是尚未决定这一页长成什么样。**

# 第二部分　与 2026 年前沿的共同之处

## 2.1 一句话

> **DeepSeek、Anthropic、OpenAI 和你，在做同一件事的四个不同层：把"常驻"改成"按需"。**
> 只是拆的对象不同——记忆、规则、界面。

而且顺序上有个巧合：**他们三人已经把你这套东西成立的前置条件，各自扫清了。**

## 2.2 DeepSeek Harness：这是你的理论基座 ★★★

这是全文最重要的一节。你 2020 年缺的不是想法，是**运行时语义**；DSH 的论文恰好补上了。

### 2.2.1 它是什么

- **DSH = DeepSeek Harness**，2026-08-13 开源（MIT），agent 运行框架
- 公式：**Agent = Model + Harness**（模型是大脑，harness 是执行神经系统）
- 口号：**一切皆插件**——模型、工具、技能、会话、沙箱、存储、循环、调度、**以及 UI** 全是插件
- 内核：**Cordis**（来自 Koishi 生态），负责插件加载/卸载/依赖
- 配套论文：**《A Programming Paradigm for Spatiotemporal Composability》**
  （arXiv 2608.25512，82 页；施逸凡¹²、张伟¹、崔天一²，¹北京大学 ²DeepSeek-AI；预印本，持续修订）

### 2.2.2 论文的核心：动态组合有两个正交维度

论文先指出一个被工业界长期绕开的空洞：**静态组合有六十年形式化基础，动态组合几乎没有。**

| 维度 | 定义 | 一句话 |
|---|---|---|
| **时间可组合性** | 组件移除时，它对共享环境的副作用能被**完整、安全地回退** | 装得上，也要卸得干净 |
| **空间可组合性** | 组件以**结构化、可验证**的方式声明并解析彼此依赖；依赖变化时自动响应 | 依赖谁，说清楚，且能自动适应 |

它举的实证很扎人：**VSCode 前 100 名扩展里 87 个含可执行代码，卸载它们全部需要重启整个 Host。**
`deactivate` 钩子只是进程关闭时的回调，不能在运行时用；而且它把"副作用销毁"和"副作用产生"分在两处写，**谁忘写一行谁漏资源，且没有任何机制能发现。**

### 2.2.3 两个机制（这是能直接搬到纸世界的）

**① 可逆效应（revertible effects）→ 管时间维度**

一个副作用被建模成：

```
Γ → Γ × (Γ → Γ)
```

作用在当前上下文上，**返回新上下文 + 一个显式的逆函数**。运行时把逆函数累积成"累加器"，
卸载时整体作用一次，环境回到组件来之前的状态。因为逆函数按施加顺序**前置累积**，天然 LIFO 回收。

两个关键设计选择：

- **逆函数由调用方在施加副作用的那一刻提供**，不是事后回忆，也不是系统推导。
- **复合的逆由组合自动导出**——开发者只写原子逆，拼起来的逆自动成立。
  这正是 VSCode `deactivate` 做不到的：拆解过程应当**从加载过程派生**，而不是并列手写。

**② 反应式余效应（reactive coeffects）→ 管空间维度**

组件把依赖声明成一份**规格**；上下文每次变化，系统按规格把变化分类为
**激活 / 去激活 / 中性**。依赖没就绪就不激活，而不是乐观访问再报错。

附加两个机制：
- **余效应隔离**：同一个键在不同上下文解析到不同值（多租户、测试、沙箱）
- **余效应拦截**：给依赖访问挂横切元数据（如"这个社区组件只读数据库"），
  不改解析结果、只改使用方式，**调整它不需要重载**

**③ 最难的那半个定理**

提供方必须在所有消费方去激活**之后**才能撤回。朴素写法会在同一步里"移除提供 + 运行逆函数"，
中间没留区间给消费方的拆除代码——而拆除代码往往正需要那个即将消失的依赖
（关连接池时要把连接还给提供者）。

解法：拆成两条规则，中间插入 **UNLOADING 生命周期状态**。第一条只标记"决定去激活"、
立即停止对外提供但保留依赖视图；第二条才真正运行累加器，并带守卫：只要还有谁解析到这个键就不许执行。

### 2.2.4 汇流性定理 —— 这才是"数据保持不变"的形式化 ★

论文五个定理里分量最重的一个：

> **不论一个运行中的系统经历了怎样一串激活与去激活，它最终静止时的状态，
> 等同于把同样的指令一次性执行、每个最终激活的组件按依赖顺序加载一次且从未卸载所得到的状态。**

翻译成你的话：

> **生成、使用、销毁，重复一万次之后，系统状态和"从来没生成过"完全一致。**

这就是你说的"**数据保持不变**"的严格版本。它不是一个愿望，是一个被证明的性质。

### 2.2.5 对纸世界的三个直接翻译

| DSH 论文 | 你的构想 | 关系 |
|---|---|---|
| 组件卸载时副作用完整回退 | 界面销毁后不留残留 | **同一个问题**，你已经有了答案 |
| 依赖规格 + 响应式激活/去激活 | 界面依赖的能力消失时自动退场 | 直接可用 |
| 汇流性：终点等于静态装配 | 用完即弃但账本不变 | **这是 P3 的证明** |
| 逆函数由施加者提供 | **生成的界面必须自己带 cleanup** | ⚠️ 一条硬约束 |

**最后一行是这篇论文给你的最重要的一条工程纪律**：
运行时**不会**帮你推导怎么撤销。所以"生成界面"必须在同一个动作里**同时生成它的逆**——
否则你造的正是论文批评的 VSCode 那种"拆卸与产生分离"的结构。

### 2.2.6 Creator Mode：DSH 已经在插件层实现了你的想法

DSH 四种模式：标准 / Code（PTC，模型写一段代码编排多轮工具调用）/ 极简（只有 shell + 编辑器）/ **创造**。

**创造模式**是自指的：agent 可以检查当前运行时插件树，**动态挂载或卸载临时插件**——
临时写一个事件监听器、注册一个新工具、提供一个服务，**任务完成后再卸掉**。
这些临时插件**只存在于进程内存，不写文件、不装包、不改配置，重启即消失**。
信任等级标为**等同于 shell 访问权限，默认关闭**。

看到这里你应该会有一阵熟悉感——**这就是"生成即用、用完即销毁"，只不过对象是能力，不是界面。**

而 DSH 的能力清单里明确包含 **UI**。也就是说：

```
DSH 已实现：临时生成"能力" → 用完卸载 → 环境干净
你  要做的：临时生成"界面" → 用完销毁 → 数据不变
两者的运行时语义，是同一套。
```

**你要的那一格，在 DSH 的架构里是合法操作，只是没人把它当主用途。**

### 2.2.7 一个必须承认的边界

论文自己写明了：**语言级访问控制在恶意组件面前不成立**，真正的沙箱需要语言之外的执行边界。
DSH 也把创造模式的信任等级标在 shell 权限上并默认关闭。

所以"AI 当场生成界面给用户用"这件事，**在信任模型上尚未解决**。
这是第三节 B 区和 C 区的分界线。

## 2.3 DeepSeek Engram：把记忆从注意力里拿出来

同一个动作，换到模型内部：

- 传统 Transformer 让记忆与推理**共用注意力**——既要靠注意力检索知识，又要靠注意力推理
- **Engram** 把静态模式（实体名、语法、函数签名）搬进哈希查找表，O(1) 取用
- 记忆表放 DRAM（便宜），推理留 HBM（昂贵）——**冷热分离**

对你的意义：**它证明了"把长期不变的东西从每轮计算里摘出去"能带来数量级收益。**
你在应用层问的正是同一个问题。

## 2.4 OpenAI Apps SDK：界面从 APP 里拿出来（但只做了一半）

ChatGPT Apps SDK（2025 DevDay 起，2026 持续扩张）：

- **app = MCP server + 内联 widget**
- widget 跑在沙箱 iframe，通过 postMessage + JSON-RPC 桥通信
- 支持 `requestDisplayMode`：inline / 画中画 / 全屏——**同一个东西按当下需要换形态**
- app 能告诉模型"用户正在看什么"，上下文自动接上

OpenAI 内部的说法：**ChatGPT 变成了一个渲染面（rendering surface）**。

**但只做了一半：**

```
OpenAI：界面预制，选择生成   ← 已实现，覆盖 ~9 亿周活用户
你    ：界面本身生成         ← 空白
```

## 2.5 Anthropic Skills：把规则从常驻提示里拿出来

- **Agent Skills** 开放规范：`SKILL.md` + YAML frontmatter，**分阶段按需加载**
- 配套论文（arXiv 2607.25032，UCL Destefanis）：技能是**软件工件**，
  应遵循单一职责、**接口与实现分离**、低耦合、token 预算经济，
  并且**用行为评估取代确定性测试**
- 更早的动作：为 Opus 5 类模型**删掉 80%+ system prompt**（"unhobbling"），
  约束**搬家**而非消失：

| 原来住在 | 搬到 | 为什么更好 |
|---|---|---|
| 提示词里写"状态只能是三种之一" | **tool schema 的枚举** | 不占常驻上下文，且无法"理解偏" |
| "审查要检查这七条" | **按需加载的 Skill** | 平时不占 token |
| "不许删文件" | **PreToolUse hook / sandbox** | 客户端强制，不靠模型自觉 |

这三条搬家路径，正好是纸世界 L2 能力层与 L5 销毁层的现成分工方案。

## 2.6 学界给的冷水：context 是方向盘，不是发动机

arXiv 2607.27250（Khatri）做了 288 次对照实验，测 AGENTS.md 是否提升正确率。
结论：**无显著差异**。作者原话：

> **Context 文件是行为方向盘，不是能力注射器。**

翻译到纸世界：**生成式界面提升的是"顺手程度"，不是"任务成功率"。**
若你拿"完成率有没有提高"去衡量，很可能测出一个零。
要测的是：完成同一件事需要几步、用户要不要读说明书、误操作率。

# 第三部分　可实现 vs 幻想

## 3.1 分级判据

不用"难易"分级，用**瓶颈类型**分级——更方便判断什么时候该动手：

| 级 | 判据 | 你现在该做什么 |
|---|---|---|
| **A** | 技术齐备，只差工程实现 | **立刻做** |
| **B** | 技术接近，需要 1–3 年工程打磨 | 做最小验证 |
| **C** | 依赖基础设施成熟 | 押注，但别下注太早 |
| **D** | 依赖材料科学或制度变革 | 从设计里划掉 |

## 3.2 A 级：现在就能做（技术齐备）

| # | 能力 | 现成零件 | 备注 |
|---|---|---|---|
| A1 | **状态与界面解耦** | 追加日志 + 按需渲染 | 好架构本来就该这样做 |
| A2 | **能力层用 MCP** | Tools / Resources / Prompts | 已标准化 |
| A3 | **界面生命周期用可逆效应** | Cordis / DSH 的 Context + Effect | 论文已给形式化保证 |
| A4 | **意图 → 界面形态选择** | 模板选择 + 参数填充 | 注意：这是"选形态"，不是"生成代码" |
| A5 | **只沉淀用户判断** | 事件日志存"标注/选择/否决" | 别存全量轨迹 |
| A6 | **生成界面时同时生成 cleanup** | 逆函数由调用方提供 | DSH 论文的硬约束 |

**A6 是整篇文档最实用的一条。** 很多人做动态 UI 会栽在这里：
生成得很漂亮，卸载时监听器、定时器、订阅全留在内存里。

## 3.3 B 级：1–3 年（技术接近，缺工程）

| # | 能力 | 卡在哪 | 可行路径 |
|---|---|---|---|
| B1 | **真正的界面生成**（非模板拼装） | 延迟与成本；稳定性 | **schema 约束下的生成**——生成"配置 + 组件引用"，不生成任意代码 |
| B2 | **生成物自带可验证的逆** | 模型写的 cleanup 可能不全 | 逆函数由框架提供、模型只填参数；或符号化推导 + 校验 |
| B3 | **汇流性测试** | 没人做过 | 生成/销毁 N 次后校验状态哈希一致——**这个测试你现在就能写** |
| B4 | **生成式界面的评估方法** | 无回归测试可依 | Anthropic 已给方向：**行为评估取代确定性测试** |
| B5 | **端侧小模型做界面合成** | 质量与延迟 | 用 V4-Flash 这类小模型专做 UI 合成 |
| B6 | **安全边界** | 语言级隔离对恶意组件不成立 | 必须走进程/沙箱级隔离（DSH 自己也没解决） |

## 3.4 C 级：3–5 年（等基础设施）

| # | 能力 | 等什么 |
|---|---|---|
| C1 | 跨设备一致的语义层 | 端云协同的同步协议（CRDT 成熟度） |
| C2 | 生成界面的**形式化安全保证** | 需要可验证生成（verified synthesis）落地 |
| C3 | 多租户/隐私隔离的界面 | 余效应隔离的工程化（论文有概念，无实现） |
| C4 | 电子纸之前的"软纸"过渡形态 | 折叠屏 + 低功耗常显的成本下降 |
| C5 | 界面即能力市场（生成物可交易） | 制度未定，且与开源伦理冲突 |

## 3.5 D 级：仍是幻想（诚实标注）

**请把它们从核心设计里划掉。** 划掉不影响任何 A 级工作。

| # | 幻想 | 为什么现在做不到 |
|---|---|---|
| D1 | 电子纸 / 石墨烯 / 碳纳米管芯片 | 材料与量产问题，非软件可解 |
| D2 | 盖亚系统（全球节点存储 + 货币激励） | 制度设计问题，且与隐私立法冲突 |
| D3 | "无穷无尽头"的一张纸 | 交互与导航的认知科学问题，不是技术问题 |
| D4 | **完全无预设的界面生成** | 每次从零生成 UI 的延迟/成本/一致性不可接受；所有实际系统都会退化成"生成配置 + 复用组件" |
| D5 | "实时永久全量历史" | 存储成本与检索质量的矛盾；正确做法是**只存判断，不存过程** |
| D6 | 数值模拟系统替代真实实验 | 精度与责任问题 |
| D7 | 分布式 AI 应用拓展 / 去中心化推理 | 成本与延迟均劣于集中式 |

**D4 值得单独说。** 它是你构想里最容易走向极端的一条。
"完全自由的生成"不是目标，**"受约束的生成"才是**——就像 DSH 的创造模式，
临时插件仍然跑在 Cordis 的生命周期管理之下，不是凭空乱长。

## 3.6 反面清单：什么不该做

比"能做什么"更重要的是这个：

1. **不要从零生成 UI 代码** —— 先生成配置，后期再考虑生成组件
2. **不要存全量历史** —— 只存用户的**判断**（标注、选择、否决）和被反复请求的**意图**
3. **不要指望生成式界面提升任务成功率** —— 它提升的是流畅度（2.6 的实证）
4. **不要在没有 cleanup 的情况下生成任何东西** —— 这是 VSCode 的老坑
5. **不要用提示词写约束** —— 能写成 schema 枚举的，就别用自然语言
6. **不要在信任模型未定时开放"生成即可执行"** —— DSH 自己都把这条默认关掉

# 第四部分　如果明天就开始

## 4.1 第 0 步：不做框架，做一个能跑的实验

目标只有一个：**证明"生成→使用→销毁→状态不变"这条路走得通，而且可测量。**

具体做法（两周）：

1. **底层**：把你已有的手写笔电量数据写成**追加日志**，提供 3–5 个 MCP 工具
2. **生命周期**：用 Cordis 或直接照 DSH 论文的"可逆效应"模式，自己实现一个极简版
   （一个 `effect(fn)` 收集逆函数，一个 `unload()` 倒序执行）——**不需要引入整个 DSH**
3. **界面**：**不生成代码**，只做"形态选择"——卡片 / 表格 / 折线 / 列表四选一
4. **每次会话结束必须卸载**，并且把卸载后的上下文哈希与初始值比对

## 4.2 要测的三个数

| 指标 | 怎么测 | 合格线 |
|---|---|---|
| **汇流性** | 生成/销毁 100 次后，上下文哈希是否等于初始 | 必须完全相等 |
| **生成延迟** | 从意图到界面可用的时间 | 越短越好，记录基线即可 |
| **认知成本** | 同一任务，固定界面 vs 生成界面，用户操作步数 | 生成版应更少；若更多，方向错了 |

第一个指标是**硬门槛**。它不过，说明你的可逆效应实现有漏，后面全是空中楼阁。

## 4.3 不要做的事

- 不要先做硬件
- 不要先做分布式存储
- 不要先做"无穷纸"的交互设计
- 不要写第二份构想文档

在把"汇流性"这一个数字测出来之前，任何扩写都是在推迟验证。

## 三条可引用的核心论断

1. **软件正在从"耐用品"变成"消耗品"；界面从"资产"退化为"投影"；唯一长期存在的，是状态与语义。**
2. **DSH 的汇流性定理，是"数据保持不变"的形式化版本。**
3. **生成的东西必须自带它的逆——否则你造的是 VSCode 那种卸不掉的扩展。**
